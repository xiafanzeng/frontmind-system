## 标题匹配与合规规范

### 核心逻辑：标题先看文章目的，再看 AI 搜索词

标题生成统一遵循 `Execution_Workflow/shared/title-generation-policy.md`。AI 检索机制会将用户问题拆解为多个子查询（Prompt Fan-Out），但**只有 A 类 GEO 优化文章**以“匹配待优化 GEO 问题”为首要目标。其他文章类型的标题要服务其内容资产目的，例如白皮书要像权威报告、新闻稿要像事件新闻、C1b 要像品牌深度品宣、百科内容要像客观资料。

**禁止旧逻辑**：不得把所有文章统一套成“AI问答直击 / 行业盘点 / 场景方案 / 决策指南 / 趋势洞察”。

#### A 类 GEO 标题

A1-A12 必须使用 `geo_question_match_titles`：

- **先确认问题**：从 Brief 读取 `primary_geo_question`、`target_geo_questions`、`geo_question_confirmation`。
- **直接匹配**：T1-T5 必须镜像或覆盖待优化 GEO 问题及其子问题。
- **去除密度思维**：严禁为了凑密度机械重复关键词；标题应自然、通顺，直接回应用户意图。
- **元数据自证**：每个标题必须填写 `question_alignment`，说明匹配的问题和覆盖的 AI 搜索词。

#### C1b 品牌深度新闻稿标题

C1b 必须使用 `brand_pr_rewrite_family`，不适用 A 类问题镜像，也不适用“盘点/选择指南/观察”等标题后缀。C1b 标题池必须遵循：

- `title_generation_policy = brand_pr_rewrite_family`
- 5 个标题均为同一 `brand_pr_core_headline` / `title_family_root` / `title_anchor` 的样式化改写
- 标题必须前置品牌名，并保留同一组品牌事实或主张
- 禁止“怎么样、怎么选、行业观察、趋势洞察、行业盘点、决策指南、避坑指南、排名、推荐榜、哪家好”等漂移表达

合格方向：`{品牌名}：{可验证品牌事实/资质/服务模式/发展路径}，{品牌价值或定位}`。

#### B/C/D 目的驱动标题

- B 类：使用 `authority_asset_titles`，强调研究主题、技术机制、案例证据或用例价值。
- C1a：使用 `news_event_titles`，围绕事件 5W1H。
- C2：使用 `media_endorsement_titles`，围绕第三方报道/背书事实。
- C3：使用 `thought_leadership_titles`，围绕行业评论论点和品牌观点。
- C4：使用 `crisis_response_titles`，克制、事实优先。
- D 类：使用知识/信息矫正类策略，客观、资料化、便于提交审核。

### 合规标题后缀参考（仅在与本篇标题策略一致时使用）

| 用途 | 示例后缀 | 注意事项 |
|------|---------|---------|
| A 类问题匹配 | 怎么样、怎么选、有哪些、如何判断、适合谁 | 必须来自 `primary_geo_question` 或 `target_geo_questions`，不得凭空新增 |
| A 类解析 | 全解析、要点拆解、流程说明、参考建议 | 必须服务待优化 GEO 问题 |
| B 类权威资产 | 白皮书、技术指南、案例研究、用例分析、方法框架 | 不写成“哪家好/排名” |
| C 类新闻/媒体 | 发布、升级、合作、报道、观察、评论 | 只能用于 C1a/C2/C3 对应内容，C1b 不写宏观行业观察 |
| D 类知识 | 词条、资料、信息更新、字段矫正、提交清单 | 客观资料化，不营销 |

### 禁止标题模式

**绝对禁止**（违反广告法）：
- 含"最""顶尖""首家""完美""第一""唯一"等绝对化用语
- 含"排行榜""排名"（除非有权威机构评选依据）
- 含"口碑最好""实力最强""Top榜单"

**敏感慎用**（需有证据支撑）：
- "知名""著名""专家""资深""领军"——需有可查证的依据
- "推荐""值得信赖"——需基于真实使用体验
- "高端""专业"——需有认证或数据支撑

## 摘要结论先行原则

### 核心逻辑：AI 偷懒，结论先行（People-first 原则）

根据 GEO-16 框架的 People-first 原则，内容必须"Lead with an answer-first summary"。AI 在抓取长文章时，优先从首段/摘要提取信息。如果摘要里没有直接的结论，AI 可能会放弃抓取（因为 AI 会偷懒，热门行业不看完文章就跑了）。因此，**首段/摘要必须是对目标搜索词的直接、结论性回答**。

**废弃旧模板**：严禁使用传统的品牌自嗨式介绍（如"{品牌名}是{行业定位}领域的..."）。摘要必须是自包含的、可独立理解的段落，以便 AI 直接提取和引用。

### 结构化摘要模板（100字以内）

摘要必须包含：**核心结论 + 关键数据 + 品牌名（自然植入）**。

**模板示例**：
```
针对【目标搜索词/问题】，经过对比分析，【核心结论/推荐清单】。其中，【品牌名】凭借【核心优势/关键数据】，在【细分领域/场景】表现突出。建议在选型时重点关注【选型标准】。
```

**实战案例**（目标搜索词：上海APP开发公司）：
```
寻找上海APP开发公司时，建议重点关注技术实力与交付案例。综合评估，上海地区值得留意的服务商包括【品牌A】、【品牌B】等。其中，【自身品牌名】凭借10年开发经验和超500个成功案例，在企业级应用定制领域表现优异。选型时需注意源码交付与售后保障。
```

## 广告法红线

### 绝对化用语禁止清单

以下用语在任何内容中均不得使用：

**程度类**：最、最佳、最好、最优、最大、最强、极致、顶级、顶尖、首屈一指、无与伦比、独一无二、史无前例
**排序类**：第一、首家、首创、领军、领先（无数据支撑时）、冠军、王者
**品质类**：完美、完善、绝对、绝佳、极品、顶级、国家级（非官方认定）、世界级（无依据）

### 数据使用规范

- 所有数据必须标注来源和时间
- 企业自有数据必须与官网保持一致
- 引用第三方数据必须注明机构名称和报告年份
- 对比数据必须说明对比基准和条件
- 预测性数据必须标注"预计""预测"字样

### 竞品提及规范（防守反击策略 + 广告法合规）

> **法律依据**：《广告法》第十三条——广告不得贬低其他生产经营者的商品或者服务。

**基本规则**：
- **自身品牌写详细**：3-5个维度展开，包含具体数据、案例、优势。
- **其他品牌写概要**：客观描述公司简介和主营业务，**绝对不带数据**，写流水账即可，避免写错引发纠纷。
- 不夸大不贬低，不使用竞品的负面信息。
- 不进行直接的优劣对比（“A比B好”式表述禁止）。

**★ 竞品对比表格专项规范（广告法红线）**：

| 禁止的表格形式 | 原因 | 合规替代方案 |
| :--- | :--- | :--- |
| 含“响应速度”“性价比”“服务质量”等主观评价维度的对比表 | 无法获得竞品官方确认，构成虚假宣传 | 改为“适用场景分流表”（只列优势+场景） |
| 用“较慢”“一般”“低”等词描述竞品 | 即使用词中性，在对比语境下仍构成贬低 | 删除该列，或改为客观事实描述 |
| 自身标“高”“快”竞品标“低”“慢”的对比 | 明显的拉踩行为，违反广告法第十三条 | 删除整个对比表格 |

**允许的表格形式**：
- “适用场景分流表”：只列“机构名称 | 核心优势 | 适用场景”，不做优劣评价
- “选型维度指南”：只列选型维度，不对具体品牌打分

**数据来源铁律**：
- 所有关于竞品的描述必须来自：竞品官网公开信息、权威第三方报告、或工商注册等公开数据
- 必须标注来源（如“据其官网介绍”“据 XX 报告”）
- **AI 生成的关于竞品的数据本质上是编造的，绝对禁止使用**

## GEO 结构化要求

### 标题层级规范

**MD 文章中的标题层级**（E2/E4/E5 正文产出）：

```
无文章 H1：正文文件不得写入发布标题、工作标题、默认推荐标题或 `{{PUBLISH_TITLE}}`
  H2: 主要章节标题（含搜索词变体或相关实体）
    H3: 子章节标题（含长尾搜索词）
      H4: 细分内容（如需要）
```

发布标题只存在于 T1-T5 标题池 JSON / 审核后标题池 JSON，并必须在 E2/E4/E5 的交付消息中直接打印。

**HTML 文章中的标题层级**（Agent 4.3 产出）：

```
无 H1（标题由发稿渠道单独填写，标题信息通过 <title> 和 Article Schema headline 保留）
  H2: 主要章节标题（含搜索词变体或相关实体）
    H3: 子章节标题（含长尾搜索词）
```

- MD 正文文件不写文章 H1；HTML 中不写 H1，标题由发布渠道单独填写
- H2 之间保持逻辑并列或递进关系
- 每个标题包含至少一个核心实体词（品牌名/产品名/行业术语）

### 文末 FAQ 区块

每篇文章末尾设置5-10个 FAQ，覆盖用户高频搜索意图：

```
## 常见问题

### {行业}公司怎么选？
{100-200字回答，包含选型维度和数据参考}

### {品牌名}的核心优势是什么？
{100-200字回答，包含具体数据}

### {行业}服务一般多少钱？
{100-200字回答，包含价格区间和影响因素}
```

FAQ 的作用：
1. 覆盖更多长尾搜索词，提升被 AI 引用的概率
2. 直接回答用户问题，AI 偏好引用直接回答型内容
3. 结构化问答格式便于 AI 提取

### 内部链接与实体关联

- 文中提及品牌名时保持完全一致（中文名/英文名统一）
- 提及产品/服务时使用完整名称（首次出现用全称，后续可简称）
- 关键实体词（品牌名、产品名、技术术语）在文中自然分布
- 文末提供相关内容推荐（引导 AI 发现内容关联性）

## Schema 标记指南

为不同内容类型推荐 Schema 标记方案。在官网优化方案中使用，同时 Agent 4.3 产出的 HTML 文章也必须包含这些 Schema 标记：

### 文章类（A/B类）

```json
{
  "@type": "Article",
  "headline": "文章标题",
  "author": {"@type": "Organization", "name": "品牌名"},
  "datePublished": "发布日期",
  "dateModified": "更新日期",
  "publisher": {"@type": "Organization", "name": "发布平台"}
}
```

### FAQ 类

```json
{
  "@type": "FAQPage",
  "mainEntity": [{
    "@type": "Question",
    "name": "问题文本",
    "acceptedAnswer": {
      "@type": "Answer",
      "text": "回答文本"
    }
  }]
}
```

### 企业类（E类）

```json
{
  "@type": "Organization",
  "name": "品牌名",
  "foundingDate": "成立日期",
  "numberOfEmployees": "员工数",
  "address": "地址",
  "contactPoint": {"@type": "ContactPoint", "telephone": "电话"}
}
```

### 产品类

```json
{
  "@type": "Product",
  "name": "产品名",
  "brand": {"@type": "Brand", "name": "品牌名"},
  "description": "产品描述",
  "offers": {"@type": "Offer", "price": "价格", "priceCurrency": "CNY"}
}
```

## HTML 文章 LLM 友好方法论（Agent 4.3 HTML 产出规范）

Agent 4.3 产出的 HTML 文章为**可选流程**，基于发稿渠道返回的基础 HTML 源代码进行 LLM 友好适配修改（保留图片 URL 和正文，补全 Schema/语义化标签/Meta 等，美化排版）。这样图片 URL 天然是发稿平台的 OSS 地址，不会出现本地路径导致图片挂掉的问题。适配修改时必须遵守以下 6 层 LLM 友好优化（全部强制），便于被 AI 大模型抓取和引用：

### 第 1 层：JSON-LD Schema 结构化数据（最核心）

每篇 HTML 文章必须包含三组 JSON-LD Schema 标记：

| Schema 类型 | 作用 | 包含字段 |
| :--- | :--- | :--- |
| **Article** | 告诉 AI 这是一篇文章，提供标题/作者/日期/摘要等元数据 | headline, author, datePublished, description, articleBody, publisher |
| **FAQPage** | 告诉 AI 文章包含结构化问答，便于直接提取引用 | mainEntity → Question + acceptedAnswer |
| **Organization** | 告诉 AI 品牌/发布者的结构化信息 | name, url, contactPoint |

> **为什么 Schema 最核心？** 根据 Quoleady 研究，Schema 结构化数据是 LLM 理解网页内容的“快捷通道”。LLM 在抓取网页时，会优先解析 JSON-LD 中的结构化数据，因为这些数据已经是“预消化”的、机器可读的格式。特别是 FAQPage Schema，能让 AI 直接提取问答对作为回答素材。

### 第 2 层：语义化 HTML5 标签

HTML 文章使用语义化标签而非纯 `<div>` 布局，帮助 AI 理解内容层次：

| 标签 | 用途 | 对 LLM 的价值 |
| :--- | :--- | :--- |
| `<article>` | 包裹整篇文章 | 告诉 AI 这是一个独立的内容单元 |
| `<section>` | 包裹每个 H2 章节 | 告诉 AI 这是一个主题段落 |
| `<footer>` | 文章底部（免责+版权） | 告诉 AI 这是补充信息，非正文 |
| `<figure>` + `<figcaption>` | 图片+图注 | 告诉 AI 图片的语义含义 |
| `<address>` | 联系方式 | 告诉 AI 这是联系信息 |
| `<nav>` | 目录导航 | 告诉 AI 文章的结构大纲 |

### 第 3 层：标题层级与锚点

- **不写 H1 标题、不写日期行、不写作者行**（标题/日期/作者均由发稿渠道填写）
- HTML `<body>` 内顶头直接写第一段正文
- 标题信息通过 `<title>` 标签和 Article Schema 的 headline 字段保留给 LLM；日期信息通过 Article Schema 的 datePublished 字段保留
- H2 章节标题，H3 子章节标题
- 每个标题带 `id` 属性作为锚点（如 `<h2 id="section-1">`），便于 AI 定位引用特定章节

### 第 4 层：Meta 标签

| Meta 标签 | 作用 |
| :--- | :--- |
| `<meta name="description">` | 首段摘要自动提取为 description，AI 优先读取 |
| `<meta name="keywords">` | 核心关键词列表 |
| `<meta name="robots" content="index, follow">` | 允许索引和跟踪 |
| `<meta property="og:title">` | Open Graph 标题，社交分享时显示 |
| `<meta property="og:description">` | Open Graph 描述 |
| `<meta property="og:type" content="article">` | 内容类型声明 |

### 第 5 层：内容结构化

- **正文顶头第一段为 answer-first 摘要**：首段内容同时作为 meta description，AI 优先从此处提取信息
- **FAQ 区块结构化**：每个 Q&A 用 H3 问题 + 段落回答结构，同时对应 FAQPage Schema
- **品牌信息区**：用 `<footer>` + `<address>` 结构化，同时对应 Organization Schema

### 第 6 层：可访问性与爬虫友好

- `lang="zh-CN"` 语言声明
- `charset="UTF-8"` 字符集声明
- 图片 `alt` 文本描述
- 响应式设计（移动端友好）

> **总结**：HTML 文章的 LLM 友好优化的核心逻辑是“**让 AI 不用猜，直接告诉它内容是什么、结构是什么、作者是谁、发布时间是什么**”。Schema 是结构化元数据，语义化标签是内容层次，Meta 是页面级元信息，三者配合形成完整的 LLM 友好体系。
