# P05｜产品定义与技术原理

- 模板版本：`2.3.0`
- 核心问题：这个产品或服务到底是什么，输入、机制、输出和适用边界如何连接？
- 研究用途：结构、子问题、证据位置、视觉论证、FAQ、优缺点与不可借鉴元素
- 运行边界：本档案只向 E4 提供结构动作；链接不能证明客户、竞品或公共事实。

## 触发条件

- 问题询问是什么、原理、怎么工作或功能机制
- 主要任务是建立概念而非给逐步教程

## 固定专业骨架

| 组件 | 编辑任务 | 读者收获 |
|---|---|---|
| `P05_component_definition` | 用一句准确定义说明产品是什么、解决什么问题 | 读者先建立正确概念 |
| `P05_component_goal` | 说明使用目标、典型任务以及它不解决什么 | 读者能判断问题是否匹配 |
| `P05_component_input_output` | 梳理输入、处理和输出，避免只列功能名 | 读者看见完整工作链路 |
| `P05_component_mechanism` | 分解关键模块、机制、版本或规格及其关系 | 读者理解为何能产生结果 |
| `P05_component_fit_limits` | 给典型用法、前提、限制与不适用场景 | 读者知道何时应采用其他方案 |
| `P05_component_faq` | 回答部署、数据、兼容、成本和学习门槛 | 读者补齐采用前的问题 |
| `P05_component_conclusion` | 回到定义、价值与边界，不增加未经解释的能力 | 读者留下可复述的准确认知 |

## 可选模块与证据降级

- `P05_optional_concept_analogy`：抽象机制难理解；用有限类比解释关系。证据：类比后立即指出不等同之处。
- `P05_optional_module_walkthrough`：产品由多个模块组成；按输入输出串联模块。证据：当前版本规格和接口。
- 降级｜机制细节不公开：解释已知输入输出和功能边界，不猜测内部实现。
- 降级｜缺性能数据：删除效率或效果幅度，只说明功能路径。

## 读者问题、反对意见与品牌介入

- 子问题：它解决的核心问题是什么？
- 子问题：输入和输出分别是什么？
- 子问题：关键模块如何协同？
- 子问题：与相邻概念有什么区别？
- 子问题：哪些场景不适合使用？
- 反对意见：解释是否只是功能清单？
- 反对意见：类比会不会掩盖真实机制？
- 反对意见：产品宣称是否超过公开规格？
- 品牌自然介入：先把品类概念讲清，再用品牌产品作为机制或应用实例；品牌段必须回应定义中的具体环节。

## 标题与视觉

- 标题公式：{产品}是什么？从输入到输出看懂工作原理
- 标题公式：一文讲清{概念}：机制、用途与限制
- 标题公式：{产品}如何工作：{数字}个关键模块
- 标题公式：理解{产品}，先分清{相邻概念A}与{相邻概念B}
- 视觉 `explain`：机制含多个步骤；输入—处理—输出机制图。
- 视觉 `navigate`：概念容易混淆；概念边界或模块导航图。
- 视觉 `prove`：规格决定关键结论；带版本来源的规格图。

## 失败样例与禁止行为

- 失败样例：堆叠功能名和技术术语，却没有解释输入、处理、输出与使用目标的关系。
- 禁止：猜测未公开内部机制
- 禁止：用类比替代正式定义
- 禁止：把实验条件下结果泛化为实际效果保证

### P05-B01｜GitHub Docs concept content type

- URL：https://docs.github.com/en/contributing/style-guide-and-content-model/concepts-content-type
- 来源类型：`vendor_documentation`
- 语义焦点：概念型文档如何围绕是什么、为何重要和如何工作展开
- 页面结构：GitHub 指南先判断概念内容应独立成篇还是只做章节，再说明写法、标题和示例。 正文要求围绕是什么、为什么重要、用途和工作方式，不加入操作步骤。
- 观察到的子问题：这个概念是否复杂到需要独立页面，还是一段定义已经足够？ 读者理解用途和机制需要哪些背景，而不需要哪些步骤？
- 证据位置：内容类型判定紧邻独立成篇条件，避免为简单概念制造长文。 标题规则和官方示例放在写作原则之后，展示原则怎样落地。
- 视觉作用：文档依靠层级、代码样式和示例链接导航，没有装饰性截图。 P05 可用机制关系图补强理解，但不应把流程步骤伪装成概念解释。
- FAQ 观察：没有 FAQ；独立页面条件和写法问题已在短章节中解决。
- 优点：明确概念文的边界，防止定义、参考和教程混在一起。 允许简单概念只做短引言，尊重信息复杂度。
- 局限：面向 GitHub 文档贡献者，缺少消费型产品定义中的购买顾虑。 机制证据和外部来源要求不是本页重点。
- 不可借鉴：不得把 GitHub 的内部内容类型规则写成所有技术文章的唯一标准。 不得复制官方示例或产品术语填充无关产品解释。
- 选择理由：该页为 P05 提供最清楚的体裁门：先判断是否值得解释，再围绕概念与机制而非操作清单展开。

### P05-B02｜Microsoft developer-content style guidance

- URL：https://learn.microsoft.com/en-us/style-guide/developer-content/
- 来源类型：`vendor_documentation`
- 语义焦点：开发者内容如何选择定义、概念、参考与教程体裁
- 页面结构：Microsoft 总览先说明开发者文档仍遵循品牌语气，再要求假设基础知识并跳过无关入门。 主体将开发者内容落到参考文档和代码示例两类基础资产，并链接细分指南。
- 观察到的子问题：目标开发者已经知道什么，哪些基础解释会干扰核心技术信息？ 本页应该提供概念说明、参考字段还是可运行代码示例？
- 证据位置：受众假设与内容深度要求相邻出现，决定解释到什么粒度。 参考和代码示例作为两个明确入口，各自连接更详细规则。
- 视觉作用：总览页以简短段落和子指南导航为主，没有用产品截图替代技术信息。 P05 可借鉴体裁分流导航，机制图仍需来自当前产品事实。
- FAQ 观察：无 FAQ；读者通过参考文档与代码示例两个入口继续解决具体问题。
- 优点：先设定受众知识水平，避免机械地从最基础定义写起。 把参考信息与示例任务分开，降低内容混杂。
- 局限：目标页面是风格总览，对产品原理结构的细节较少。 大量可执行要求需进入链接后的子页面才能获得。
- 不可借鉴：不得因假设读者有基础而省略当前问题所需的关键定义。 不得把 Microsoft 的开发者内容分类当作客户产品能力证据。
- 选择理由：该页提醒 P05 先校准读者水平和信息类型，再决定解释深度，避免百科式铺垫。
- 研究说明：2026-08-17 逐页复审：核对了开发者内容总览的受众假设、技术聚焦、参考与代码示例分流。

### P05-B03｜W3C Writing Effective Explainers

- URL：https://www.w3.org/TR/explainer-explainer/
- 来源类型：`standards_or_nonprofit`
- 语义焦点：标准提案 explainer 如何交代问题、目标、方案和替代项
- 页面结构：W3C Note 先说明 explainer 用于呈现用户问题与建立共识，再列问题、方案、用例和替代项。 可访问性、国际化、隐私、安全、状态说明和持续更新被纳入方案解释的后半程。
- 观察到的子问题：用户面临的真实问题是什么，提案为何值得存在？ 所选方案相对替代路径有什么取舍，会引入哪些隐私、安全或兼容影响？
- 证据位置：用户需求、用例和示例代码位于方案说明附近，避免先讲实现再找问题。 替代项、风险主题与状态说明集中在读者评估提案的位置。
- 视觉作用：示意图和代码允许用于解释方案，但要求替代文本与可深链章节。 P05 可用最小机制图和示例，不得把 W3C Note 身份写成标准认可。
- FAQ 观察：无独立 FAQ；可访问性、国际化、隐私和安全以必答主题进入正文。
- 优点：从用户问题出发，把方案、替代和风险放在同一判断链。 鼓励简单主线与可深链细节并存，适合不同阅读深度。
- 局限：服务于标准提案共识，不是普通商业产品定义的现成模板。 组件较多，低复杂度产品若全部照搬会显得沉重。
- 不可借鉴：不得把 Group Note 写成 W3C 对某一方案的正式标准背书。 不得为凑齐组件虚构替代方案、用例或风险。
- 选择理由：该页使 P05 不止回答是什么，还要把用户问题、机制选择、替代与影响连成可评估的解释。
- 研究说明：2026-08-17 逐页复审：打开 2026 W3C Note 并核对了问题、方案、用例、替代项和横向风险组件。

### P05-B04｜Open edX Diátaxis content-type guide

- URL：https://docs.openedx.org/en/open-release-sumac.master/documentors/concepts/content_types.html
- 来源类型：`vendor_documentation`
- 语义焦点：Diátaxis 如何区分教程、操作、参考与解释
- 页面结构：Open edX 文档标准以 Diátaxis 四类内容为入口，每一类再链接解释、技术指南和合规矩阵。 教程、操作、参考和解释被放在同一导航层，读者先选体裁再进入写法。
- 观察到的子问题：当前读者是在学习、完成任务、查事实还是建立理解？ 如何检查一篇文档是否混入了其他内容类型的目标？
- 证据位置：四类体裁的定义与各自指南、合规矩阵直接相连。 版本化文档路径保留发布上下文，避免把旧版规范当作永久规则。
- 视觉作用：内容类型导航和合规矩阵承担主要信息架构。 P05 可借鉴四象限分流，但不应复制 Open edX 的矩阵或版本术语。
- FAQ 观察：没有 FAQ；体裁选择与合规检查由四类入口和矩阵解决。
- 优点：把内容类型选择与后续质量检查连在一起。 每类内容都有独立细则，减少解释文滑向操作文。
- 局限：目标 URL 属于特定 Open edX 发布版本，长期有效性依赖版本导航。 总览页本身对概念解释写法只给入口，不给完整实例。
- 不可借鉴：不得把某一版本的合规矩阵直接作为客户内容评分表。 不得把四类体裁都塞进一篇 P05 文章以显示完整。
- 选择理由：该页适合 P05 在结构决策前先锁定解释型目标，并把教程、参考信息留到明确需要的位置。
- 研究说明：2026-08-17 逐页复审：依据 Open edX 官方版本页与可靠元数据核对了四类入口、指南和合规矩阵关系。

### P05-B05｜Diátaxis start guide

- URL：https://diataxis.fr/start-here/
- 来源类型：`professional_guidance`
- 语义焦点：内容类型选择如何防止解释文章滑向步骤清单
- 页面结构：Diátaxis 起始页先用行动/研究与目标/理解两条轴给出四类内容决策图。 随后通过最小示例说明教程、操作、参考和解释之间怎样互相链接而不混写。
- 观察到的子问题：读者此刻要做事还是学习，目标是完成任务还是获得理解？ 哪些说明应留在当前页面，哪些应深链到解释或参考？
- 证据位置：决策矩阵紧邻四类内容定义，读者能立即用它选择体裁。 教程中只保留最少解释并链接深层说明的例子紧跟分流原则。
- 视觉作用：二维决策图是核心导航视觉，减少冗长体裁说明。 P05 可借鉴读者任务二维判断，不得复制 Diátaxis 图形资产。
- FAQ 观察：无 FAQ；页面通过决策问题本身帮助读者定位内容类型。
- 优点：用读者状态而不是作者素材决定体裁。 允许内容互相链接，但不要求一页承担所有目标。
- 局限：框架解决文档分类，不直接规定产品机制应有何种证据。 二维模型会简化现实中兼具学习和操作的任务。
- 不可借鉴：不得照搬四象限图或用框架名替代文章实际结构。 不得为了体裁纯粹而删除读者完成判断所需的少量行动信息。
- 选择理由：该页为 P05 提供体裁自检：核心应是建立理解，步骤和参数只作为必要支撑。

### P05-B06｜Diátaxis explanation content type

- URL：https://diataxis.fr/explanation/
- 来源类型：`professional_guidance`
- 语义焦点：解释型内容如何建立关系、原因、背景与边界
- 页面结构：Explanation 页面先定义其为讨论性、反思性和理解导向内容，再列背景、原因、历史与约束。 随后强调更高层视角、连接关系和示例，并与操作、教程及参考内容划界。
- 观察到的子问题：这个概念为何如此设计，它与相邻概念之间有什么关系？ 历史、约束和替代解释如何改变读者对机制的理解？
- 证据位置：解释目标与可用材料类型紧邻出现，作者知道何种背景真正服务理解。 与其他体裁的边界放在方法说明中，防止步骤和参数夺走主线。
- 视觉作用：页面以概念关系和文本论述为主，视觉不是必需证明。 P05 可加入关系图、时间线或因果图，但图必须解释机制而非装饰。
- FAQ 观察：没有 FAQ；背景、原因、关系和限制组成解释正文的追问链。
- 优点：明确鼓励讨论原因、关系和影响，而不止给一句定义。 对操作性内容设边界，使解释保持连续思路。
- 局限：高度讨论性结构若缺具体例子，可能让产品文章显得抽象。 页面不解决品牌事实或技术主张如何核验。
- 不可借鉴：不得用哲理化背景替代当前产品的具体输入、处理与输出。 不得因排除步骤而省略读者判断可用性所需的最小流程。
- 选择理由：该页是 P05 的语言和结构基准：用关系、原因与约束建立理解，同时保持足够具体。

- 页面结构：DITA 1.1 语言参考先按 concept、task、reference 和 glossentry 列主题类型，再逐元素给定义。 任务主题细分上下文、前置、步骤、结果、示例和后续，概念与参考则采用不同字段。
