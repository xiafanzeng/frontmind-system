# P08｜教程与操作

- 模板版本：`2.3.0`
- 核心问题：读者如何在明确版本和前提下完成操作、验证结果并处理常见失败？
- 研究用途：结构、子问题、证据位置、视觉论证、FAQ、优缺点与不可借鉴元素
- 运行边界：本档案只向 E4 提供结构动作；链接不能证明客户、竞品或公共事实。

## 触发条件

- 问题包含如何做、设置、安装、使用或排错
- 读者需要可复现步骤而非概念解释

## 固定专业骨架

| 组件 | 编辑任务 | 读者收获 |
|---|---|---|
| `P08_component_direct_answer` | 说明操作目标、完成标志和适用版本 | 读者知道做完应该看到什么 |
| `P08_component_prerequisites` | 列明权限、工具、材料、备份和前置条件 | 读者可在开始前排除阻塞 |
| `P08_component_steps` | 按输入—动作—预期结果—检查点组织可复现步骤 | 读者可以不猜测地逐步执行 |
| `P08_component_validation` | 提供成功验证、常见错误定位和恢复方法 | 读者能判断是否真正完成 |
| `P08_component_limits` | 说明不适用版本、危险动作和替代办法 | 读者避免把教程用错场景 |
| `P08_component_faq` | 回答权限、回滚、数据影响和高频报错 | 读者能独立处理常见障碍 |
| `P08_component_conclusion` | 回收结果和下一步维护动作 | 读者完成闭环而非停在最后一步 |

## 可选模块与证据降级

- `P08_optional_quick_path`：存在安全的默认路径；先给最短成功路径。证据：明确适用版本和默认条件。
- `P08_optional_rollback`：操作可能改变数据或系统；给备份和回滚步骤。证据：恢复点、权限和验证。
- 降级｜无法确认版本：写明适用范围并避免具体界面位置猜测。
- 降级｜高风险操作缺安全前提：删除操作细节，改为联系专业人员或官方支持。

## 读者问题、反对意见与品牌介入

- 子问题：需要哪些权限和准备？
- 子问题：每一步的预期结果是什么？
- 子问题：如何确认操作成功？
- 子问题：最常见失败原因是什么？
- 子问题：何时应回滚或换用其他方法？
- 反对意见：步骤是否在当前版本仍有效？
- 反对意见：省略的前置条件会不会导致数据损失？
- 反对意见：教程是否能在失败后恢复？
- 品牌自然介入：品牌产品只在对应操作界面、工具或支持路径中出现；先明确任务，不把教程写成产品漫游。

## 标题与视觉

- 标题公式：如何完成{任务}：从准备到验证的完整步骤
- 标题公式：{产品}{功能}操作指南：{数字}步完成
- 标题公式：{任务}失败怎么办？常见原因与排查顺序
- 标题公式：{版本}下使用{功能}的正确方法
- 视觉 `navigate`：步骤较长；步骤导航或进度图。
- 视觉 `explain`：界面或物理操作关键；真实截图标注或步骤示意。
- 视觉 `prove`：成功状态可验证；真实结果截图或校验输出。

## 失败样例与禁止行为

- 失败样例：步骤只有动作没有前提、预期结果和校验，读者失败后也没有恢复路径。
- 禁止：对高风险医疗或系统操作给无安全前提的细节
- 禁止：使用过期界面截图冒充当前版本
- 禁止：省略备份、权限或不可逆影响

### P08-B01｜Microsoft guidance for step-by-step instructions

- URL：https://learn.microsoft.com/en-us/style-guide/procedures-instructions/writing-step-by-step-instructions
- 来源类型：`vendor_documentation`
- 语义焦点：逐步说明如何为每一步提供动作、反馈和结果
- 页面结构：微软样式指南先区分单步与多步流程，再规定编号、祈使句、动作粒度和界面路径写法。 位置提示、最终确认动作和无障碍注意事项紧跟对应写法，形成可直接执行的编辑清单。
- 观察到的子问题：一个步骤是否只包含一个可观察动作，必要位置是否在动作前交代？ 单步、分支步骤与界面菜单路径分别应采用什么格式？
- 证据位置：每条写作规则后立即给短例，读者可对照判断动作句是否合格。 关于 OK、Apply 等收尾动作和菜单分隔符的要求放在具体场景旁，而非集中成抽象原则。
- 视觉作用：页面主要依靠正确示例、编号列表和界面文本格式展示操作写法。 P08 可借鉴界面路径与动作结果并置，但不得把样式示例当成产品界面截图。
- FAQ 观察：没有 FAQ；单步、多步、界面路径和可访问性问题由分节规则与示例解决。
- 优点：动作粒度和句式规则明确，能直接约束教程步骤的可执行性。 把位置放在动作前，降低读者执行到一半才发现路径条件的概率。
- 局限：它是微观写作规范，不提供完整教程的前置条件、验证和故障恢复骨架。 示例围绕微软界面语言，不能替代具体产品版本的实际操作核验。
- 不可借鉴：不得照搬示例中的菜单、按钮或产品路径到无关软件。 不得把一句一动作机械化为省略必要解释、风险或分支条件。
- 选择理由：该页适合校准 P08 的步骤句：位置明确、祈使动作单一、执行结果可观察。

### P08-B02｜GitHub Docs tutorial content type

- URL：https://docs.github.com/en/contributing/style-guide-and-content-model/tutorial-content-type
- 来源类型：`vendor_documentation`
- 语义焦点：教程如何围绕一个可完成项目建立学习路径
- 页面结构：GitHub 先界定 tutorial 面向已有基础的读者和真实问题，再规定引言、顺序步骤、故障排查与结尾。 引言写受众、前置知识、预期成果和完成样例；正文以可运行项目推进，结尾只给少量下一步。
- 观察到的子问题：读者开始前应具备什么知识，完成后能解决哪个现实问题？ 在哪些步骤最可能失败，成功结果和恢复路径怎样被读者识别？
- 证据位置：完整代码和实际输出放在对应步骤内，概念说明则链接到专门文档。 故障排查紧跟可能出错的工作流，结论以二至三个相关后续动作收束。
- 视觉作用：代码块、命令结果和必要截图承担验证作用，不依靠装饰视觉。 完成项目的可见样例在引言中建立预期，后续步骤持续回到这个结果。
- FAQ 观察：没有独立 FAQ；常见失败集中在 troubleshooting，后续学习放在 conclusion。
- 优点：教程围绕一个完整真实工作流，而不是把零散功能串成目录。 受众、前置条件、结果和失败恢复都有固定位置。
- 局限：内容模型针对 GitHub Docs，标题和术语规则不必适用于所有出版渠道。 默认读者已完成 quickstart，不适合完全零基础的首次上手材料。
- 不可借鉴：不得复制 GitHub 的标题禁词或下一步数量为所有品牌的绝对规则。 不得把链接外置原则用来省略本步骤真正需要的操作上下文。
- 选择理由：该页提供 P08 的完整教程闭环：明确成果、顺序实践、结果验证、故障处理和下一步。
- 研究说明：2026-08-17 逐页复审：核对了 tutorial 的受众定义、引言合同、步骤组织、代码上下文、故障排查和结尾要求。

### P08-B03｜GitHub Docs authoring templates

- URL：https://docs.github.com/en/contributing/writing-for-github-docs/templates
- 来源类型：`vendor_documentation`
- 语义焦点：模板如何稳定呈现前置条件、步骤、排错和后续动作
- 页面结构：模板页按 concepts、reference、how-to、quickstart、tutorial 等内容类型分别提供可复制骨架。 how-to 强调权限和操作，quickstart 压缩为短工作流，tutorial 则增加受众、项目成果和分步实践。
- 观察到的子问题：当前任务需要短上手、单一操作，还是以学习为目的的完整项目？ 权限、前置条件、代码上下文和进一步阅读应放在哪一类模板位置？
- 证据位置：模板注释逐段说明字段用途，并要求发布前移除占位说明。 完整代码示例与预期结果留在执行步骤中，复用内容和扩展阅读通过链接承接。
- 视觉作用：该页本身是文本模板集合，视觉价值在稳定层级和代码块位置。 P08 可借鉴不同任务复杂度的骨架选择，不应让模板注释出现在公开正文。
- FAQ 观察：没有 FAQ；不同内容类型模板和内嵌注释承担作者决策支持。
- 优点：清楚区分 how-to、quickstart 与 tutorial，避免所有操作文都套同一篇幅。 前置条件、过程、代码和后续资源在模板中各有明确容器。
- 局限：这是作者起稿工具，不是经过用户验证的成品教程案例。 模板包含 GitHub 特有 frontmatter 与 reusable 语法，迁移时需要剥离。
- 不可借鉴：不得把模板注释、占位文本或 frontmatter 直接发布。 不得因模板有固定章节就忽略实际任务的分支、风险和成功检查。
- 选择理由：该页帮助 P08 按任务复杂度选骨架，并确保权限、代码上下文和下一步不被遗漏。
- 研究说明：2026-08-17 逐页复审：逐一查看了 how-to、quickstart、tutorial 等模板的引言、步骤、代码与扩展阅读槽位。

- 局限：方法论层级较高，没有给具体产品的输入、界面或成功输出。 刻意减少解释，若独立使用可能不足以支持陌生或高风险任务。

- 选择理由：该页为 P08 提供用户目标导向和现实分支设计，防止教程退化成菜单功能清单。

- 局限：适合学习型教程，不直接覆盖熟练用户解决紧急问题的短指南。 没有具体领域的安全、权限或版本示例。

- 选择理由：该页补足 P08 的学习型路径：早期成果、明确预期、失败提示和逐步建立信心。

- 页面结构：文章先区分 troubleshooting guide 与普通手册，再用关键要点解释问题收集、组织、写法和维护。 正文按常见问题识别、症状—原因—解法、分支决策、视觉辅助和真实用户验证推进。
- 观察到的子问题：用户遇到的是哪个可观察症状，最可能原因和最小修复动作是什么？ 哪些问题需要是非分支、截图、错误消息或升级到支持渠道？
- 证据位置：真实支持问题和常见错误被作为主题选择依据，而非作者凭空列故障。 更新与用户验证放在发布后维护部分，强调排障文档随产品变化。
- 视觉作用：建议使用症状—解法表、决策树、截图、错误消息和必要流程图。 视觉用于缩短定位路径；装饰图不能替代实际界面或错误状态。
- FAQ 观察：没有独立 FAQ；高频问题本身被转成可搜索的排障条目和分支路径。
- 优点：以真实症状开头，能让读者先定位而不是从头重做全部流程。 强调持续更新、术语一致和真实用户验证。
- 局限：商业技术写作站的建议缺少一套公开实证方法来证明每项最佳实践。 页面提供方法而非具体产品的已验证故障数据库。
- 不可借鉴：不得虚构错误消息、原因或修复成功率。 不得用通用决策树替代产品版本、权限和数据影响检查。
- 选择理由：该页适合强化 P08 的故障分支：从症状定位到原因、动作、验证和升级渠道。
- 研究说明：2026-08-17 逐页复审：核对了指南定义、问题收集、症状组织、分支形式、视觉类型、测试和更新建议。
